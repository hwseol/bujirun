# 자연어로 코스 만들기 — 설계

> 목표: "한강 따라 5km", "근처 공원 몇 군데 돌아서 30분", "남산까지 갔다가 돌아오기"처럼 말하면
> 그 근처의 공원·강변·명소를 엮은 코스를 만들어 준다.
> 원칙: **서버 비용을 거의 쓰지 않는다.** 요청 1건 = SQLite 조회 몇 번 + TMAP 1~2회. 운영 중 LLM 호출은 없다 (큰 모델은 개발 때 한 번, 6절).
> 작성: 2026-10-09

## 1. 비용 원칙

| 비용 | 줄이는 방법 |
|---|---|
| LLM | 문장 해석은 **폰 안의 작은 전용 모델 + 규칙**으로 한다 (거리·시간·모양·테마·장소 이름). 서버에는 해석이 끝난 구조화된 요청만 간다 (6절) |
| 서버 CPU | 공원·강변·명소 데이터는 **미리 받아 SQLite에** 넣어 둔다 (두루누비 trails.db와 같은 방식). 요청마다 외부 API를 부르지 않는다. 후보 조합 고르기는 직선거리 계산뿐이라 수 ms |
| TMAP | 경로 후보를 **기하 계산으로 먼저 거르고** 가장 좋은 1~2개만 TMAP에 보낸다 (지금 순환 코스는 최대 6회). 같은 출발점(100m 격자)+같은 요청은 7일 캐시 |
| 헛 요청 | 폰이 해석 결과를 칩으로 먼저 보여주고(`5km` `순환` `공원`), 사용자가 확인 버튼을 눌러야 서버를 부른다. 잘못 알아들은 문장이 서버 비용이 되지 않는다 |
| 남용 | 사용자당 하루 20건 (기존 TMAP 카운터 `charge()` 공유) |

## 2. 흐름

```
[폰] 문장 입력 ─→ 내장 모델 + 규칙 (순수 Kotlin) ─→ 칩으로 표시, 사용자가 수정 가능
                                                        │ "코스 만들기"
                                                        ▼
[서버] POST /routes/plan {start, intent}
        1) places.db에서 출발점 주변 후보 조회 (테마별)
        2) 후보 조합을 직선거리×우회계수로 평가 → 상위 2개
        3) TMAP 보행자 경로 (경유지 ≤ 5) → 거리 어긋나면 1회 보정
        4) remove_spurs / 겹침 검사 (기존 순환 코스 코드 재사용)
        ◀─ 코스 1~2개 + 지나는 곳 이름 ("반포한강공원 → 서래섬")
[폰] 지도 미리보기 → 저장 / 바로 달리기 (기존 SuggestScreen 흐름)
```

## 3. 문장 해석 (폰, `course/IntentParser.kt`)

| 항목 | 알아듣는 표현 | 없을 때 |
|---|---|---|
| 거리 | `5km` `5키로` `3.5킬로` `800m` `오천 미터`(숫자만) | 시간이 있으면 시간 × 내 평균 페이스(기록 없으면 걷기 6km/h, 달리기 9km/h), 둘 다 없으면 3km |
| 시간 | `30분` `1시간` `한 시간 반` | — |
| 모양 | 순환(기본) / `왕복` `갔다가 돌아` → 왕복 / `까지` `로 가는` → 편도 | 순환 |
| 테마 | `한강` `강` `천` `하천` `강변` → 강변 · `공원` `숲` → 공원 · `명소` `관광` `구경` → 명소 · `호수` | 없음 (지금 순환 코스와 같음) |
| 회피 | `오르막 없이` `평지` `언덕 피해` | — |
| 장소 이름 | 테마·숫자·조사를 빼고 남은 명사구 (`남산`, `서울숲`, `석촌호수`) | — |

- 장소 이름은 서버의 places.db에서 이름으로 찾는다 (출발점에서 가까운 것 우선). 없으면 TMAP POI 검색 1회 (무료 플랜 포함).
- 해석 결과는 칩으로 보여주고 탭해서 고칠 수 있다. 사용자가 고친 값이 정답이다.

## 4. 장소 데이터 (서버, `places.db`, 월 1회 갱신)

| 데이터 | 출처 | 비용·조건 |
|---|---|---|
| 도시공원 (전국 약 2만 곳: 이름, 종류, 좌표, 면적) | 공공데이터포털 **전국도시공원정보표준데이터** | 무료, 출처 표시. 기존 data.go.kr 계정으로 활용신청 |
| 관광 명소 | 한국관광공사 **TourAPI (국문 관광정보)** — 두루누비와 같은 기관 | 무료, 출처 표시. 활용신청 필요 |
| 강변·하천 산책로 (한강, 탄천, 양재천, 중랑천 …) | OpenStreetMap 한국 추출본에서 하천 옆 보행로 선을 뽑아 저장 | 무료, ODbL — "© OpenStreetMap 기여자" 표시. 서버에서 1회 변환 (Overpass를 요청마다 부르지 않음) |

네이버·카카오 지도 데이터는 약관상 수집할 수 없어서 쓰지 않는다 (C4 때와 같은 이유).

## 5. 코스 짜기 (서버, `planner.py`, 순수 함수 + 테스트)

목표 거리 D, 출발점 S. 우회계수 k ≈ 1.25 (도로망이 직선보다 긴 비율, 실제 결과로 보정).

- **공원·명소 순환**: S에서 반경 D/2.5 안의 후보 중 1~3곳을 고른다. 모든 조합 × 방문 순서(최대 3! = 6)에 대해 `k × (S→a→b→S 직선 합)`이 D에 가까운지 + 큰 공원·이름난 곳 가점 + 방향이 한쪽으로 몰리지 않았는지로 점수. 짧으면 공원 안을 한 바퀴 도는 경유점(공원 중심 둘레)을 더해 채운다. 상위 2개만 TMAP.
- **강변**: S에서 가장 가까운 강변 산책로 진입점 P까지 거리 a. 남은 D − 2a를 강변 위에서 쓴다.
  - 순환: 강변을 따라 (D − 2a)/2 … 가서 다른 진입점으로 나와 돌아온다.
  - 왕복: 강변을 따라 (D − 2a)/2 가서 되돌아온다 (왕복은 겹침 검사 생략).
  - a가 D/2보다 크면 "강변이 너무 멀어요 (편도 2.4km)"라고 알려주고 그냥 순환 코스를 제안.
- **장소까지 편도/왕복**: 목적지 T까지 TMAP 1회. 거리가 지정됐는데 T가 그보다 멀면 알려준다.
- **오르막 회피**: 2단계. 지금은 칩만 받아 두고 무시하지 않도록 "아직은 오르막을 고려하지 못해요"라고 표시 (지형 데이터 비용 검토 후).

TMAP 결과가 목표에서 ±12% 넘게 벗어나면 경유점을 비율만큼 당기거나 밀어 1회만 다시 요청한다.

## 6. 큰 모델은 한 번, 작은 모델은 매번 (증류)

큰 모델은 **개발 PC에서 한 번만** 돌려 (실제로는 Gemini API로 진행: 학습용 3.8 Flash, 평가용 3.1 Pro) 두 가지를 만든다. 매 요청은 **폰 안의 작은 전용 모델**이 처리한다. 운영 중 LLM 비용 0원, 서버 부담 0.

### 6-1. 문장 해석 모델 (폰에 내장)

| | |
|---|---|
| 하는 일 | 문장의 글자마다 꼬리표 달기(거리/시간/모양/테마/회피/장소 이름/기타) + 문장 전체 분류(순환·왕복·편도). 범용 대화 모델이 아니라 이 일만 하는 모델 |
| 구조 | 음절 임베딩 + 작은 양방향 GRU(또는 1D CNN) + 꼬리표 출력. 파라미터 약 30~50만 개, int8로 **0.5MB 이하** (APK 30MB 한도 안) |
| 실행 | TFLite 같은 라이브러리 없이 **순수 Kotlin**으로 행렬 곱 몇 번. 폰에서 수 ms, 오프라인 |
| 숫자 처리 | 모델은 "어디가 거리인지"만 찾고, `5키로` `한 시간 반` `오천 미터` → 값 변환은 규칙(3절)이 한다. 숫자 변환은 규칙이 틀릴 일이 없고 모델은 문맥(띄어쓰기 없음, 오타, 반말, 순서 바뀜)을 맡는다 |
| 안전망 | 모델 확신이 낮은 꼬리표는 칩을 회색으로 보여주고 사용자가 고친다. 규칙 해석과 모델 해석이 다르면 칩에 둘 다 후보로 |

**학습 데이터 (Claude가 한 번 생성)**
- 다양한 사람·상황을 바꿔 가며 문장 약 2만 개 + 정답 꼬리표 생성: 출퇴근 전 짬, 여행지 숙소, 아이와 산책, 오타·줄임말(`5k` `한바퀴` `ㄱㄱ`), 지역명 수백 개.
- 다른 프롬프트로 만든 **평가용 500문장**은 학습에 안 쓰고, 그중 100개는 사람이 직접 확인.
- 기준: 평가셋 완전일치 95% 이상이면 출시, 아니면 틀린 유형만 더 생성해 재학습.
- PC(CPU)로 학습 수 분. 학습 스크립트·데이터 생성 스크립트는 저장소 `tools/nlu/`에, 생성 데이터는 저장소 밖.

### 6-2. 장소 다듬기 (서버 places.db, 한 번 + 새 장소만)

공공데이터 공원 목록은 이름만 있다. Claude 배치(50% 할인)로 한 번 돌려 장소마다:
- **별칭**: `뚝섬` → 뚝섬한강공원, `올팍` → 올림픽공원, `석촌` → 석촌호수 — 6-1 모델이 뽑은 장소 이름을 이걸로 찾는다
- **달리기 적합도 1~5** (둘레길 유무, 크기, 종류: 근린공원 vs 어린이공원)
- 결과는 DB 칼럼으로 저장. 월 1회 갱신 때는 **새로 생긴 장소만** 돌린다.

### 6-3. 비용 (한 번)

| 작업 | 모델 | 추정 |
|---|---|---|
| 학습 문장 2만 + 평가 500 | Claude Opus 5.5, 배치 | 약 1~2만 원 |
| 장소 2만 곳 별칭·적합도 | Claude Opus 5.5, 배치 | 약 1~2만 원 |
| 운영 중 | 폰 내장 모델 | **0원** |

Haiku 5.5로 하면 10분의 1 이하지만 학습 데이터 품질이 모델 품질이라 한 번 쓰는 데는 큰 모델 권장.
API 키는 개발 PC 환경변수로만, 서버·저장소·앱에 두지 않는다.

## 7. 앱 화면

추천 화면에 세 번째 탭 **말로 만들기**.

- 입력창 + 예시 칩 (`한강 따라 5km` `공원 돌아서 30분` `가까운 명소 들르기`)
- 입력하면 바로 해석 칩 줄 (`5km` `순환` `강변`) — 탭해서 수정
- "코스 만들기" → 결과 카드 1~2개: 지도, 거리, 지나는 곳 이름 → 저장 / 바로 달리기
- 출처 표시: 공공데이터·관광공사·OSM 중 쓰인 것만

## 8. 단계

| 단계 | 내용 | 확인 |
|---|---|---|
| N1 | 규칙 해석(숫자·단위 변환) + 말로 만들기 탭 (해석 칩까지) | JVM 테스트 |
| N2 | `tools/nlu/`: Claude로 학습·평가 데이터 생성 → 작은 모델 학습 → 가중치 내보내기 → Kotlin 추론 + 규칙과 결합 | 평가셋 95%, 같은 입력에 Python과 Kotlin 출력 일치 테스트 |
| N3 | places.db: 도시공원 + 강변 산책로 sync, Claude 배치로 별칭·적합도 | 백엔드 테스트, 서울 몇 곳 수동 확인 |
| N4 | planner.py (공원 순환, 강변 순환/왕복, 장소 편도/왕복), `/routes/plan`, 캐시 | 백엔드 테스트(TMAP 주입), 에뮬레이터 |
| N5 | TourAPI 명소 추가 | |

## 9. 결정이 필요한 것

1. **Anthropic API 키** (console.anthropic.com, 결제 수단 등록): 개발 PC에서 한 번 돌리는 데만 씀. 환경변수 `ANTHROPIC_API_KEY`로 직접 설정 (채팅에 붙여넣지 않아도 됨).
2. 공공데이터포털 활용신청: **전국도시공원정보표준데이터** (N3), **한국관광공사 국문 관광정보 서비스** (N5).
3. 강변 데이터에 OSM 사용 (앱에 "© OpenStreetMap" 표시).
